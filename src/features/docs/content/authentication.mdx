# Authentication

Vangrex uses API keys to authenticate requests from your applications.

Your API key identifies your application and determines whether it is authorized to interact with your Vangrex resources.

For most integrations, you will create a Vangrex client using your API key and use the client to interact with workflows and executions.

## API keys

API keys are secrets.

A typical Vangrex API key looks like:

```text
vx_live_xxxxxxxxxxxxxxxxxxxxxxxxxxxxx
```

Your actual key will be generated by Vangrex.

Keep your API key private and never expose it in client-side code.

### Server-side usage

Store your API key in an environment variable:

```bash
VANGREX_API_KEY=vx_live_xxxxxxxxxxxxxxxxxxxxxxxxxxxxx
```

Then initialize the Vangrex SDK:

```ts
import { Vangrex } from "@vangrex/sdk";

const vangrex = new Vangrex({
  apiKey: process.env.VANGREX_API_KEY,
});
```

Your application can now use the authenticated client.

## Environment variables

Environment variables are the recommended way to store API keys.

For example, in a Next.js application:

```text
.env.local
```

```env
VANGREX_API_KEY=vx_live_xxxxxxxxxxxxxxxxxxxxxxxxxxxxx
```

Then:

```ts
const vangrex = new Vangrex({
  apiKey: process.env.VANGREX_API_KEY,
});
```

Do not hardcode secrets directly into your source code.

Avoid:

```ts
const vangrex = new Vangrex({
  apiKey: "vx_live_123456789",
});
```

Environment variables make it easier to keep credentials separate between development, staging, and production.

## Never expose API keys

Your Vangrex API key should not be included in browser bundles, mobile application code, or other environments where users can inspect the application.

For example, avoid:

```ts
"use client";

const vangrex = new Vangrex({
  apiKey: "vx_live_xxxxxxxxx",
});
```

Instead, keep Vangrex calls on your server.

```text
Browser
   │
   │ request
   ▼
Your Server
   │
   │ VANGREX_API_KEY
   ▼
Vangrex
```

Your frontend communicates with your own backend, while your backend communicates with Vangrex.

## Using Vangrex in a server

A typical server-side integration looks like:

```ts
import { Vangrex } from "@vangrex/sdk";

const vangrex = new Vangrex({
  apiKey: process.env.VANGREX_API_KEY,
});

export async function runWorkflow() {
  return vangrex.workflows.run("workflow_id", {
    message: "Hello from my application",
  });
}
```

The API key stays on the server and is used automatically by the SDK when making requests.

## API key environments

Use separate API keys for different environments when your Vangrex project supports them.

A common setup is:

```text
Development
    │
    └── Development API key

Staging
    │
    └── Staging API key

Production
    │
    └── Production API key
```

This prevents development credentials from being used by production applications.

It also makes credential rotation and access management easier.

## Rotating API keys

API keys should be rotated if they may have been exposed or when you need to replace credentials.

A typical rotation process is:

```text
Create new API key
       │
       ▼
Update application secret
       │
       ▼
Deploy application
       │
       ▼
Verify requests
       │
       ▼
Revoke old API key
```

Do not immediately revoke an old key before the application has been updated if that key is still required by a running deployment.

## Revoking API keys

If an API key is compromised, revoke it as soon as possible.

After revoking a key, requests authenticated with that key will no longer be authorized.

You should then:

1. Create a replacement key.
2. Update your application's environment variable.
3. Redeploy the application.
4. Verify that workflow requests succeed.
5. Confirm that the old key is no longer being used.

## Authentication errors

Authentication failures generally indicate that Vangrex could not authenticate the request.

Common causes include:

- Missing API key
- Invalid API key
- Revoked API key
- Incorrect environment variable
- API key not available in the current runtime
- Accidentally exposing or modifying the key

For example, if your environment variable is missing:

```ts
process.env.VANGREX_API_KEY;
```

may be `undefined`.

Make sure the variable is configured in the environment where your application is actually running.

## Debugging authentication

When debugging authentication, verify the configuration without printing the secret itself.

For example:

```ts
const apiKey = process.env.VANGREX_API_KEY;

console.log({
  configured: Boolean(apiKey),
});
```

Avoid logging the complete API key:

```ts
console.log(process.env.VANGREX_API_KEY);
```

Logs can be stored, forwarded, or accessed by other systems.

## Authentication with the SDK

Once the SDK is initialized, authentication is handled by the Vangrex client.

```ts
import { Vangrex } from "@vangrex/sdk";

const vangrex = new Vangrex({
  apiKey: process.env.VANGREX_API_KEY,
});

const execution = await vangrex.workflows.run("workflow_id", {
  input: "Hello Vangrex",
});
```

You generally do not need to manually attach the API key to every workflow request.

The SDK handles authentication for requests made through the client.

## Authentication architecture

A production application commonly looks like this:

```text
┌──────────────────┐
│   Your Frontend  │
└────────┬─────────┘
         │
         │ HTTPS
         ▼
┌──────────────────┐
│   Your Backend   │
│                  │
│ VANGREX_API_KEY  │
└────────┬─────────┘
         │
         │ Vangrex SDK
         ▼
┌──────────────────┐
│     Vangrex      │
└────────┬─────────┘
         │
         ▼
┌──────────────────┐
│     Workflow     │
└──────────────────┘
```

This architecture keeps your Vangrex credentials on trusted infrastructure.

## Authentication checklist

Before deploying your integration, verify:

- [ ] Your API key is stored as an environment variable.
- [ ] Your API key is not committed to source control.
- [ ] Your API key is not exposed to browser code.
- [ ] Production uses the appropriate production credentials.
- [ ] Your deployment environment has the required environment variable.
- [ ] Compromised keys are revoked and replaced.
- [ ] API keys are not printed in application logs.
